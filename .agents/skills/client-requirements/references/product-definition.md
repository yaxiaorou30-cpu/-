# 产品定义指南

## 目录

- 输入和信息状态

- 质量门禁

## 输入和信息状态

读取访谈、会议纪要、转写、合同/招标文件、现有程序、报表样例、业务制度和历史问题。为材料记录日期、来源角色和适用范围。

统一使用以下状态：

- `已确认事实`：多项可靠证据或权威材料确认；
- `甲方陈述`：某位利益相关者明确陈述，但未交叉验证；
- `观察`：从演示、系统、日志或样例直接观察；
- `推断`：分析人员根据证据得出的解释；
- `假设`：为了形成草案暂时采用；
- `待确认`：关键问题尚未回答；
- `冲突`：来源之间不一致；
- `决定`：有决策权的人已经选择并保留理由。

## 从证据到需求

按以下链条转换，不可跳步：

`来源证据 → 当前流程/问题 → 业务影响 → 期望结果 → 候选需求 → 验收方式 → 甲方确认`

“希望有大屏”“需要智能分析”“最好自动预警”只是愿望。只有在明确用户、触发条件、决策用途、频率、风险和验收信号后，才转成候选需求。

## 产品定义结构

### 1. 文档目的

说明读者、用途、状态和未确认内容的标记方式。

### 2. 问题和业务背景

描述当前流程、问题、影响、为什么现在处理。不得用功能列表替代问题定义。

### 3. 用户和 Jobs To Be Done

列出实际操作者、业务负责人、报告审核者、报告使用者、系统管理员等。分别写清其情境、任务和期望结果，并明确首版非用户。

### 4. 产品愿景和价值

用可理解的业务语言说明产品使谁在什么情境下获得什么结果。

### 5. 关键用户旅程

每条旅程包含角色、入口状态、步骤、决策点、价值实现时刻、结束状态和至少一个真实异常。

### 6. 术语表

统一“舆情事件、监测任务、有效数据、真实数据、热度、风险、预警、正式报告”等术语；不同部门使用不同含义时保留冲突直到确认。

### 7. MVP 范围

分别列出范围内、范围外、明确非目标和延期项。每个延期项说明理由或依赖。

### 8. 需求

覆盖功能、业务规则、数据、接口、权限、审计、性能、可靠性、安全、隐私、合规、可用性、可维护性和可解释性。

### 9. 成功和验收

成功指标必须定义口径、目标和测量方式。验收使用真实场景、输入样例、预期输出、允许误差和不可接受结果。

### 10. 假设、冲突和开放问题

集中列出并关联受影响的需求，避免隐藏在正文中。

## 需求写法

给每条需求分配稳定 ID，例如 `FR-001`、`NFR-PERF-001`、`BR-001`、`DATA-001`。

推荐结构：

```text
在【触发条件】下，【角色/系统】应【可观察行为】，以便【业务结果】。
异常/边界：【失败、空状态、权限或限值】。
验收：【给定输入或状态】→【执行动作】→【预期可观察结果】。
来源：【材料/角色/日期】；状态：【候选/草案/已确认/延期/拒绝】。
```

避免“快速、智能、友好、实时、全面、准确”等无口径形容词。将其转成响应时间、准确率、覆盖率、允许误报率、恢复时间、操作步数或其他可测量指标；若甲方尚不能给出数值，保留待确认。

## 质量门禁

逐项检查：

1. 必要性：能关联业务目标或风险；
2. 来源：能追溯到人、材料、观察或决定；
3. 清晰性：关键术语只有一种解释；
4. 一致性：与其他需求、现有流程和范围不矛盾；
5. 完整性：包含正常、异常、权限和数据边界；
6. 可行性：没有忽略已知技术、合规和资源约束；
7. 可测试性：能设计客观验收；
8. 原子性：一条需求不混合多个独立行为；
9. 状态真实性：未确认内容没有伪装成最终决定。

## 甲方确认

确认材料应短于内部分析材料，包含：共同目标、现状流程摘要、已确认决定、拟定范围、关键需求、明确非目标、冲突和开放问题。要求甲方逐项更正或确认，并记录确认人、日期和适用版本。
