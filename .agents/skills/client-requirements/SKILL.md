# 甲方需求获取

把需求获取视为“收集证据、形成可验证共识”，而不是让 AI 猜功能。覆盖三个连续工作流：甲方访谈、多人需求会议、产品定义。

## 基本规则

1. 先理解甲方当前工作、问题和结果，再讨论功能或技术方案。
2. 优先追问最近一次真实经历、现有材料和可观察行为；不要用“您是否需要某功能”收集愿望清单。
3. 严格标记信息状态：`已确认事实`、`甲方陈述`、`观察`、`推断`、`假设`、`待确认`、`冲突`、`决定`。
4. 未经来源支持，不把推断写成事实；未经责任人确认，不把愿望写成正式需求。
5. 每条正式需求保留来源、业务理由、状态和验收方式。
6. 对话式获取需求时一次只问一个主问题，根据回答追问；为外部会议准备材料时可以生成完整问题指南和分支追问。
7. 需求尚未确认时，不开始实现，不用技术细节掩盖业务未知项。
8. 记录必要角色和业务信息即可；敏感个人信息、账号、Cookie、内部密级数据不要写入需求材料。

## 开始工作

1. 检查仓库、已有实现、文档和 `requirements/` 下的历史材料。不要重复询问代码和文件已经能够回答的问题。
2. 判断当前模式：
   - 准备或执行一对一/小组访谈：读取 [stakeholder-interview.md](references/stakeholder-interview.md)。
   - 准备或主持多人会议：读取 [requirements-workshop.md](references/requirements-workshop.md)。
   - 把纪要、转写或想法整理成产品定义：读取 [product-definition.md](references/product-definition.md)。
   - 涉及本项目业务覆盖：同时读取 [project-domain-checklist.md](references/project-domain-checklist.md)。
3. 若用户没有指定会话目录，运行：

```powershell
python .agents\skills\client-requirements\scripts\init_requirements_session.py --topic "主题"
```

4. 脚本只创建不存在的文件，不覆盖已有记录。向用户说明会话目录，然后在其中持续更新材料。

## 工作流 A：甲方访谈

### 准备

1. 明确本次访谈必须消除的 1 至 3 个关键未知项。
2. 确定受访者角色、实际经验、决策权和可能偏见；缺少关键角色时指出覆盖风险。
3. 阅读现有程序和历史材料，将“已知”“推测”“需要甲方回答”分开。
4. 生成 60 至 90 分钟访谈计划，问题按以下漏斗排列：
   - 角色和业务背景；
   - 当前完整流程；
   - 最近一次真实案例；
   - 痛点、变通办法、频率和影响；
   - 异常、边界、权限与约束；
   - 成功标准和验收方式；
   - 遗漏人员、材料和问题。
5. 为关键问题准备“如果回答模糊，应如何追问”的分支，不预设解决方案。

### 进行或模拟访谈

1. 先邀请对方完整描述，不急于逐项盘问。
2. 一次只提出一个主问题；用复述确认理解，用“能否讲最近一次”获得具体事实。
3. 对愿望继续追问：为什么需要、现在怎么做、发生频率、失败影响、谁使用、怎样证明有效。
4. 实时记录证据和来源，不在会议中擅自解决所有冲突。
5. 结束前复述 3 至 5 个核心结论，确认遗漏、其他受访者、现有材料和下一步。

### 会后

1. 在 24 小时内整理纪要和证据台账。
2. 分离候选需求、冲突、假设和开放问题。
3. 生成给甲方确认的摘要，不把沉默视为确认。

## 工作流 B：多人需求会议

### 会前

1. 为会议写出一个可检验目标，例如“确认从发现事件到批准报告的现状流程和责任人”。
2. 检查参与者是否包含实际用户、业务负责人、决策人、领域专家和必要的技术/合规角色。
3. 指定主持人、记录人、决策人和时间管理员；人数超过 10 人时建议拆分。
4. 准备当前流程、场景、术语和已知冲突，避免从空白页面开始讨论。

### 会中

1. 宣布目标、范围、决策规则和停车场规则。
2. 先共同绘制现状流程，再讨论目标结果；将解决方案讨论与需求讨论分开。
3. 使用场景走查暴露异常：谁触发、输入是什么、谁判断、失败怎么办、谁批准、留下什么证据。
4. 对冲突记录各方立场、依据、影响和拥有最终决定权的人，不以多数发言替代决策权。
5. 优先级必须同时考虑价值、频率、风险、成本和截止日期，不能只写“高/中/低”。
6. 结束前逐项朗读决定、未决问题、责任人和期限。

### 会后

1. 发布决定日志、冲突清单、开放问题和待确认需求。
2. 明确哪些内容已经确认，哪些只是会议中的候选建议。
3. 安排异步确认或下一次专题会议。

## 工作流 C：产品定义

1. 汇总访谈纪要、会议记录、现有程序、合同/招标材料和样例输出；为每条内容保留来源。
2. 先写问题、用户、当前流程和期望结果，再写产品功能。
3. 形成右尺寸的产品定义：
   - 文档目的和读者；
   - 问题与业务背景；
   - 目标用户、非用户和 Jobs To Be Done；
   - 产品愿景与价值；
   - 关键用户旅程；
   - 术语表；
   - MVP 范围、非目标和延期项；
   - 功能需求、非功能需求和业务规则；
   - 数据、集成、权限、审计和合规；
   - 成功指标、验收标准；
   - 假设、冲突和开放问题。
4. 给需求分配稳定编号和状态：`候选`、`草案`、`已确认`、`延期`、`拒绝`。
5. 每条需求写成可验证行为，至少包含：角色/触发条件、系统行为、边界或异常、可观察结果、来源。
6. 对产品定义执行质量检查：完整性、一致性、无歧义、可行性、必要性、可测试性、可追踪性。
7. 生成甲方确认包；未经确认的内容保留显式标签，不伪装成最终 PRD。

## 对话行为

- 用户提供零散想法时，先允许完整倾倒信息，再问“还有什么材料或背景容易被遗漏？”
- 用户时间紧时，采用快速路径：集中识别最大缺口，以 `假设` 标签形成草案，随后要求复核。
- 用户希望深入时，采用辅导路径：一次一个问题，挑战薄弱假设，分段展示并确认。
- 用户粘贴长转写时，先抽取证据、角色、流程、决定、冲突和未知项，再提出高价值追问，不逐句复述。
- 用户的前提与代码或多方证据冲突时，明确指出冲突及影响，不自动选择一方。

## 完成标准

- 已记录访谈或会议的目标、参与者、范围和来源。
- 已区分事实、陈述、推断、假设、冲突和决定。
- 每个高价值需求都有业务理由、来源、状态和验收口径。
- 范围内、范围外、非目标和延期项清晰。
- 开放问题具有责任人或建议责任人、影响和期望解决时间。
- 已生成可发送给甲方确认的材料，并明确哪些内容仍未确认。
- 没有因为文档看起来完整而填造未知信息。
